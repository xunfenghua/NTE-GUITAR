# 模拟手柄重构补丁：源码对齐审查

**基准：** `docs/模拟手柄链路重构代码方案.md` 与随后贴入的重构代码草案，对照当前工作区源码核验。  
**结论：** 重构方向合理，但贴入的 C# 不是当前项目的可替换实现。字段命名、动作枚举、不可变动作的更新方式及输出 profile 构造均不匹配；应先完成本文对齐，再分阶段落地。

## 1. 草案中的确定性编译错误

| 草案代码 | 当前仓库实际定义 | 必要修正 |
|---|---|---|
| `GuitarAction.ActionType` | `GuitarAction.Type` | 替换所有 `.ActionType` 为 `.Type` |
| `GuitarAction.StringIndex` | `GuitarAction.Value`；`StringDown/Up` 中 Value 是弦号，`WheelSelect` 中 Value 是槽位 | 根据 `Type` 解读 `Value`，不要加错别名 |
| `GuitarAction.TargetSlot` | `RequiredSlot` 是音符依赖槽位；`WheelSelect` 的目标槽位存于 `Value` | 控制动作读取 `Value`；音符动作依赖读取 `RequiredSlot` |
| `GuitarAction.PageDirection` | 没有该字段；方向可由 `ScanCode` 与 WheelPreset 的上一页/下一页扫描码判断 | 映射到 `SendPageNav(direction,isDown)`，或新增显式方向字段并更新构造器 |
| `GuitarAction.IsUpStrum` | 没有该字段；扫弦方向是 `MouseButton` | 用 `MouseButton` 选择虚拟右摇杆方向 |
| nullable 按钮直接传入 `SetButtonState(button, ...)` | `ResolveStringButton` 返回 `Xbox360Button?` | 先验证非 null，再传 `button.Value` |
| `PageNavDown` / `ModeSwitchDown` 别名 | 当前枚举是 `PageNav`、`PageNavUp`、`ModeSwitchDown`、`ModeSwitchUp` | 保留既有 `PageNav` 命名；如果增加 `PageNavDown`，需全量迁移 compiler、scheduler、状态检查和测试 |
| `with { TimeUs = ... }` 修改动作 | `GuitarAction` 是 `readonly struct`，属性仅 getter，没有 `init` | 用构造器创建新动作，复制其余字段 |
| `DefaultGamepadProfile` 构造 | 若 profile 有 `StrumHoldUs`，其 `new(...)` 必须传此参数 | 补 `StrumHoldUs: StrumHoldUs`，或让 profile 从 GamepadInputTiming 推导默认值 |
| `onNoteDropped` 使用 | 当前 scheduler 没有 planner callback 接口 | 将丢弃诊断作为 planner 返回结果一并返回，再由 PlaybackService/Scheduler 记录；不要在后台编译阶段直接写 UI/播放报告 |

## 2. 当前 `GuitarAction` 可用字段及安全重建

当前模型在 `Guitar/GuitarCompiler.cs` 中定义：

```csharp
public readonly struct GuitarAction
{
    public long TimeUs { get; }
    public GuitarActionType Type { get; }
    public byte Value { get; }
    public ushort ScanCode { get; }
    public MouseButton MouseButton { get; }
    public long DeadlineUs { get; }
    public byte RequiredPage { get; }
    public byte RequiredSlot { get; }
    public GameActionResource Resource { get; }
    public FallbackPolicy FallbackPolicy { get; }
    public byte NoteNumber { get; }
}
```

更新事件时间时应通过构造器重建。下面的 helper 对应当前构造器参数：

```csharp
private static GuitarAction At(GuitarAction a, long timeUs) => new(
    timeUs,
    a.Type,
    a.Value,
    a.ScanCode,
    a.MouseButton,
    timeUs + Math.Max(1, a.DeadlineUs - a.TimeUs),
    a.RequiredPage,
    a.RequiredSlot,
    a.Resource,
    a.FallbackPolicy,
    a.NoteNumber);
```

重要：弦 Down/Up 的 `Value` 才是弦号；`WheelSelect.Value` 是目标槽；`PageNav.Value` 是目标页。对不同动作类型盲目把 Value 当 `StringIndex` 会造成页号/槽号被当琴弦。

当前动作枚举：

```csharp
public enum GuitarActionType : byte
{
    PageNav = 1,
    WheelSelect = 2,
    StringDown = 3,
    StringUp = 4,
    StrumClick = 5,
    PageNavUp = 6,
    ModeSwitchDown = 7,
    ModeSwitchUp = 8
}
```

如果需要显式的槽位回中和扫弦回中，新增 `WheelSelectUp = 9`、`StrumUp = 10` 是可行方案；但要同步修改 `GuitarScheduler.ExecuteAction`、动作排序、停止释放、手柄输出适配器。键鼠适配器必须明确忽略/折叠这两种 release 事件，避免将一个游戏鼠标点击误变成持续按住。

## 3. profile 草案需补齐

贴入的 profile 有 9 个构造参数，默认构造遗漏最后的 `StrumHoldUs`，会直接编译失败。最小修正：

```csharp
public sealed record GuitarOutputProfile(
    GuitarOutputKind Kind,
    long StringHoldUs,
    long SameStringReleaseUs,
    long DpadNeutralUs,
    long SlotHoldUs,
    long SlotSelectLeadUs,
    long PageHoldUs,
    long PageReleaseGapUs,
    long StrumHoldUs);

public static readonly GuitarOutputProfile DefaultGamepadProfile = new(
    Kind: GuitarOutputKind.VirtualGamepad,
    StringHoldUs: StringHoldUs,
    SameStringReleaseUs: SameStringReleaseUs,
    DpadNeutralUs: DpadNeutralUs,
    SlotHoldUs: SlotHoldUs,
    SlotSelectLeadUs: SlotSelectLeadUs,
    PageHoldUs: PageHoldUs,
    PageReleaseGapUs: PageReleaseGapUs,
    StrumHoldUs: StrumHoldUs);
```

目前 `GamepadInputTiming` 是 `internal static class`。若 profile 只被本程序集的 PlaybackService 使用，也保持 internal，避免无意改变公开 API。计时档位要支持键鼠 profile 时，单独提供 KeyboardMouse profile；不能把 gamepad 默认 profile 当作两种设备的通用 profile。

## 4. planner 草案的语义问题

### 4.1 D-pad 自动切向不等于先中立再按下

草案的 `SetString` 先调用旧方向 `SetButtonState(..., false)`，再调用新方向 `SetButtonState(..., true)`，最后仅 `SubmitReport()` 一次。Xbox 报告只提交最终状态；游戏不会看到“中立”那一帧，因此这不能实现规定的 DpadNeutralUs。

正确约束是：planner 安排旧方向 Up → 独立中立间隔 → 新方向 Down；controller 只提交每个时间轴事件，不在一次调用里自行吞并多个状态。若为了异常恢复需要强制清掉旧方向，可提交中立报告，但应视为一次额外的状态恢复事件并记录时间。

### 4.2 琶音窗口的约束没有覆盖整个声音事件

草案用 `nextClusterUs` 限制内声部 Down，却有路径让 Up 延长至 `nextClusterUs - requiredGap`；需要再校验：

- 新 Down 不得晚于该音的截止/容忍窗；
- 新 Up 必须在下一根 D-pad Down 前完成并留足 neutral；
- 所有 Up 不得越过第一个 PageNav、ModeSwitch、WheelSelect 屏障；
- Down 和 Up 必须使用相同弦号、音符号、页槽上下文；
- 同一时刻的 lead 需要是最高音且能在原拍点发出；若不能原拍点触发，应按明确策略丢弃该音或标记迟到，不能悄悄把 lead 推迟 42 ms。

草案虽计算了 `nextBarrierUs`，但攻击聚类只比较相邻音符的 RequiredPage/RequiredSlot 和时间差，没有要求 cluster 内每对音符有相同屏障索引；跨屏障同拍会被错误合并。分组 key 应包括 `BarrierSegmentId`（或先按屏障切段再聚类）。

### 4.3 琴弦事件不能只认配对成功的 Down

草案把配对的 D-pad Down/Up 从 passthrough 移除；未配对的 Down/Up 会保留并下传，planner 没有报告或清理异常对。应当：

- 未配对 Down：在适配阶段创建受控的最短 Up，或丢弃并记录；禁止让它悬挂；
- 未配对 Up：消除或记输入计划错误，不能直接提交给 controller；
- 相同时间戳重复 Down：先定义同弦重触发规则，不能让 Dictionary.Queue 配对跨音符配错；
- 5/6 面键不经过 D-pad 排程，但仍须保留 Up 配对、超时保护和控制屏障裁剪。

### 4.4 WheelSelectUp 的裁剪条件不足

`FindNextControlAfter` 需要包括 `WheelSelect`、`PageNav`、`ModeSwitchDown`，并以动作上下文/序号作 generation。只比较 `expectedSlot` 不足以排除“同一个槽位重新选中后，较旧的 NeutralizeSlot 到达”这种 ABA 情况：旧槽和新槽数值相同，expectedSlot 检查仍会通过。

推荐动作字段增加 `ControlGeneration` 或 `ActionId`：每个选槽 Down 有唯一 generation，Up 只在 `_activeSlotGeneration == expectedGeneration` 时回中。generation 不匹配时是安全 no-op。

### 4.5 屏障后的强制重新选槽需要生成/调度两端支持

PageNav 与 ModeSwitch 会清左摇杆，因此屏障后必须有显式槽位恢复动作。仅在 planner 检查“没有 WheelSelect”然后补动作仍不够：

- PageNav 目标页/模式要已知；
- 下一个音符的 `RequiredSlot` 必须取自该音符，而不是上一页状态；
- 补出的 WheelSelect 必须排在 PageNav 按下和释放之后，且留足 `SlotSelectLeadUs`；
- scheduler 状态只有在控制报告提交成功后更新；
- 若同一页随后已有有效 WheelSelect，则不得重复插入无必要动作。

当前代码中的动作名是 `PageNav`（按下）与 `PageNavUp`（释放），而不是草案写的 `PageNavDown`。处理控制状态时需要同时识别按下和释放事件。

## 5. scheduler 伪代码不能直接替换主循环

贴入的示例用了不存在的 `action.ActionType`、`StringIndex`、`TargetSlot`、`PageDirection`、`IsUpStrum`、`_useVirtualGamepad`、`GetElapsedMicroseconds()`、`RecordDiagnostic()`，而当前 scheduler 使用 `act.Type`、`Value`、`RequiredSlot`、`ScanCode`、`MouseButton`、`UseVirtualGamepad`、`Stopwatch` 和 `PlaybackDiagnosticReport`。它也省略了暂停/停止、目标窗口焦点、批量琴弦 Down/Up、timingGuard、状态恢复与 UI 进度等逻辑。

不要以一个 switch 直接替换 `GuitarScheduler` 主循环。应保留现有的等待、暂停、停止、焦点和状态机框架；只把动作执行分派改成**无等待的单动作发送**，并确保任何 report 失败都进入统一清理。新增的“迟到只跳过这一音”规则应放在琴弦 Down 的执行分支，不能覆盖控制状态错误或 Up 释放失败：

```csharp
long lateUs = Math.Max(0, nowUs - act.TimeUs);
bool noteDown = act.Type == GuitarActionType.StringDown;

if (noteDown && lateUs > options.MaxNoteLatenessUs)
{
    RecordSkippedNote(act, nowUs, "SkippedLateNote");
    continue; // 主循环继续；对应的 Up 也要从计划中安全处理
}

// 控制动作报告失败：不更新逻辑页/槽，标记状态未同步并阻止其依赖音符。
// StringUp/ResetAll 失败：进入安全清理，不可忽略，否则可能卡键。
```

如果单音 Down 被跳过，必须同时抑制其配对 Up 或将 Up 保留为无害释放；更重要的是不能因为跳过 Down 而跳过后续 Reset/控制释放事件。

## 6. “两种设备的谱面完全相同”要定义比较层级

编译期解耦可保证两种设备在**音乐计划**上的映射相同：对每个 MIDI note，计划选择相同的目标音高、弦、页、槽、模式。

经手柄适配后，D-pad 吞吐量不足时按方案会丢弃内声部；因此“最终发出的音符集合 100% 相同”与“超载时丢弃低优先级音符”不能同时成立。建议验收这样定义：

- MusicPlan：键鼠与手柄完全一致；
- GamepadTimeline：只允许因可记录的硬件容量/明确时间窗口丢弃声音事件；不得悄悄换弦、换页槽、改音高或跨屏障延迟；
- 每个 drop 有原始 MIDI 音高、时间、弦、目标页槽、丢弃原因。

同理，25/17 ms 是新假设，不是“稳定识别”实锤。目标游戏 60 Hz 采样并不自动保证 25 ms 脉冲至少被采到一次；要用诊断曲（单弦重复、四方向轮播、翻页后同槽、快速换槽、扫弦）逐档验证。

## 7. 建议的修订落地顺序

1. 先按本文修正字段与枚举，让规划器接口能映射当前 `GuitarAction`。
2. 把 `UseVirtualGamepad` 从三个音乐规划器的决策参数移除；导出并对比纯音乐计划。
3. 写 planner 的 Down/Up 配对、屏障分段、主音选择和 drop 诊断；避免一开始就同时改 scheduler。
4. 改 `VirtualGamepadController` 为无 Sleep/Timer 的单报告方法，所有状态只由 scheduler 线程提交。
5. 在 `GuitarAction` 增加显式 slot/strum release 事件，并更新排序和编译器。
6. 将事件分派接入现有 scheduler 框架，保留 pause/stop/focus/cleanup。
7. 先用较长脉冲确认无漏采，再逐档降低时序；对照 diagnostics，而非只凭听感归因。

## 8. 第二版“定稿实现”复核

第二版已经把大部分 `GuitarAction` 字段改为当前命名，也补上 profile 的 `StrumHoldUs`、屏障分段、Down/Up 配对及槽位 generation 思路；但它仍不能按贴文直接编译或替换。

### 8.1 控制器仍有 nullable enum 编译错误

第二版 `ResolveStringButton` 返回 `Xbox360Button?`，以下两处仍把 nullable 值直接传给只接受 `Xbox360Button` 的 API：

```csharp
_controller.SetButtonState(oldBtn, false);
_controller.SetButtonState(button, isDown);
```

应在 null 检查后传 `.Value`：

```csharp
if (oldBtn is Xbox360Button oldButton)
    _controller.SetButtonState(oldButton, false);

if (button is not Xbox360Button resolvedButton) return false;
_controller.SetButtonState(resolvedButton, isDown);
```

第一处同样不能只凭 nullable 检查后传原 nullable 变量，除非语言/API 签名确实接受 nullable（当前 ViGEm API 不接受）。所以“已修复 nullable 按钮”的说明与实际代码不一致。

### 8.2 scheduler 片段仍不是当前项目的可编译片段

第二版示例仍包含以下当前代码中不存在或不匹配的名称：

| 第二版引用 | 当前源码应对齐为 |
|---|---|
| `_useVirtualGamepad` | `UseVirtualGamepad` 属性 |
| `_wheelPreset.PrevPageScanCode` | 执行方法传入的 `wheel.Preset.PagePrevScanCode`（当前名称是 `PagePrevScanCode`） |
| `diagnosticReport?.RecordSkipped(...)` / `RecordError(...)` | 当前用 `PlaybackDiagnosticReport report` 与 `PlaybackDiagnosticRecord` 记录 |
| `MaxNoteLatenessUs` | 需新增到 `GuitarCompilerOptions` 或独立 scheduler policy；目前不存在 |
| `return;`（在 `ExecuteAction` 内） | 该方法返回 `bool`，应走统一结果路径并返回 `true` 表示继续 |

该片段也没有更新 `GameStateMachine` 的页、槽和模式状态。仅成功发送手柄报告、却不更新 `state.CurrentPage/CurrentSlot/Mode`，会令后续 `IsFretReady`、`IsChordReady` 与恢复逻辑使用旧状态。状态更新必须发生在发送成功后；发送失败则保留旧状态并标记依赖它的音符不可执行。

如果迟到的 Down 被跳过，贴文以 `_suppressedStringUps[弦号]` 记住对应 Up。按弦号保存一个 bool 不能可靠标识具体 Down/Up 配对：同一弦重复音、多个编译音重叠或同弦重触发时，某音的 Up 可能被误当成另一个音的 Up。应给琴弦事件增加 pair/action identity，或在 planner 先建立成对事件，再决定成对丢弃。

### 8.3 generation 写入 `ScanCode` 可行，但需限定用途

使用 `WheelSelect.ScanCode` 暂存 generation 可避免改 `GuitarAction` 结构体，且当前 scheduler 的选槽分支以 `Value` 取槽号，不靠 `ScanCode` 选择槽，所以在**虚拟手柄专用时间轴**中可以使用。需要同时保证：

- 只在手柄适配之后覆盖 ScanCode；不能把带 generation 的动作送进键鼠路径；
- `WheelSelectUp.ScanCode` 复制同一 generation，scheduler 必须将它传入 `NeutralizeSlot`；
- 所有经过 `At(...)`、排序、或控制状态重建的动作保留 generation；
- wrap 到 1 时，旧 generation 的 release 不会仍在等待队列中；最好用更宽的独立 generation 字段，或证明活动 release 的生命周期远短于 generation 回绕时间；
- `WheelSelectUp` 的过期 neutral 仅可 no-op，不能改变 `CurrentSlot` 的逻辑状态。

### 8.4 第二版 planner 仍需修正的行为边界

- **屏障后的补槽时间：** `InjectPostBarrierWheelSelects` 在 `lastBarrierReleaseUs` 晚于 note 的目标起音时，当前写法最终把 `selectUs` 截到 `act.TimeUs`，可能把 WheelSelect 放在屏障释放前。应选择不早于屏障释放的时间，再判断是否超过 lead/late 容忍窗；超出就记录该音不可达，不要用 `Math.Min(..., act.TimeUs)` 反向越过屏障。
- **孤立 Down 补 Up：** 末尾悬挂 Down 补成 `down + StringHoldUs`，但没有先裁剪到它所在段的下一个屏障；D-pad 排程随后可能丢弃，面键排程会比较屏障，但应明确所有合成事件都在对应 segment 内完成。
- **D-pad 可用时间与同弦间隔：** `requiredGap` 分别使用 `SameStringReleaseUs` 或 `DpadNeutralUs` 做容量估算，但 `dpadAvailableTimeUs` 每次都加 `DpadNeutralUs`。若两个 profile 值不同，调度与校验会不一致。每次推进应加当前方向对应的实际 gap。
- **Lead 丢弃后内声部递补：** 最高音因容量失败后，较低音仍可能按 inner voice 的较宽顺延窗口发出。若产品规则要求“保旋律，过载丢内声部”，应在 lead 无法满足时丢弃整组或明确定义后备主音选择，不能隐式让内声部承担 lead 缺位。
- **模式/翻页上下事件分段：** 对 PageNav down/up 和 ModeSwitch down/up 各自递增 segment 是保守的，但 pending Down 仍跨 segment 留在队列里。配对时必须拒绝不同 segment 的 Down/Up 成对，或者在屏障处为未释放 Down 生成屏障前 Up 并记录；否则“先按屏障切段”目前只用于后续排程，不是配对隔离。
- **`Math.Clamp` 边界：** 使用 `Math.Clamp(value, min, max)` 前必须保证 `max >= min`。尤其 face string 的上界不应晚于下一屏障；不要用跨屏障时间作为 clamp 上限再把 Up 安排在屏障同一时刻，除非动作排序明确保证 Up 先执行且报告已成功。
- **补选槽状态：** `InjectPostBarrierWheelSelects` 在屏障后首个音符补一次槽位后立即将 `stickClearedByBarrier=false`。若后续音符的 RequiredSlot 变更但输入动作里缺失 WheelSelect，状态不会再次核对；应对每个音符比较“计划槽”与当前计划槽，而不是只用一个 bool。

### 8.5 推荐的接入边界

将第二版规划器的返回类型 `GamepadPlanResult(Actions, DroppedNotes)` 保留下来；但先建立 `MusicPlan` 与 `GamepadTimeline` 的边界。`PlaybackService` 应只对 `UseVirtualGamepad` 时间轴调用 planner，并把 `DroppedNotes` 合并进播放诊断。

在 `GuitarScheduler` 里新增 `WheelSelectUp`、`StrumUp` 两个分支，复用现有 `ExecuteAction`/诊断结构；不要照贴文替换主循环。每个分支需覆盖：成功后的控制器和逻辑状态、失败后的状态同步标记、暂停/停止时的 `ResetAll`、键鼠输出对手柄专用 release 动作的忽略，以及同时间戳的稳定优先级。

**更新结论：** 第二版的结构比第一版更接近当前类型定义，但仍不是“100% 源码对齐、可编译替换”的定稿。至少修复 8.1 与 8.2 的编译/接口问题，再处理 8.4 的事件边界，才适合开始构建验证。
