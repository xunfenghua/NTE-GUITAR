# 模拟手柄链路重构：代码方案

**目标：** 把吉他音乐规划与手柄报告时序拆开；让手柄事件非阻塞、不会越过翻页/选槽/切模式屏障；输入失败按动作记录，不因普通迟到把整曲调度拖入连锁失步。本文是供手动实现的改造单，不修改现有 `.cs` 文件。

**涉及文件：** `Guitar/GamepadInputTiming.cs`、`Guitar/GamepadActionPlanner.cs`、`Input/VirtualGamepadController.cs`、`Guitar/GuitarScheduler.cs`，以及调用它们的 `FretConverter`、`GuitarCompiler`、`HybridGuitarCompiler`、`PlaybackService`。

## 1. 现状核对：哪些已由源码证实

| 观察 | 当前实现 | 结论 |
|---|---|---|
| 手柄参数影响前期规划 | `FretConverter`、`GuitarCompiler`、`HybridGuitarCompiler` 读取 `UseVirtualGamepad`；会改变 settle、准备时间、候选代价或同弦时间 | 确实存在输出设备与音乐计划耦合 |
| D-pad 后处理塞不进屏障 | `StaggerDpad` 检查整段；若不适配则原样保留，并写 warning | 确实可能把密集段交给下游串行处理 |
| 下游串行阻塞 | `VirtualGamepadController.SetStringsBatch` 内部等待按住和 D-pad 中立时长；`GuitarScheduler` 在同一播放线程同步调用它 | 确实可能令后续动作迟到 |
| 左摇杆自动回中并发 | 选槽使用 `Timer`，回调和播放线程都在 `_sync` 锁内修改并提交同一控制器状态 | 有异步状态时序，但现有锁保护了 ViGEm 访问；源码本身不能证明存在数据竞争或未捕获异常 |
| Deadline 导致后续全跳过 | `GuitarAction` 有 `DeadlineUs`，但 `GuitarScheduler` 主循环没有通用的 `nowUs > DeadlineUs` 丢弃分支；时序保护器单独控制琴弦可执行时间 | “Deadline 超时后整曲被状态校验连锁拒绝”尚未由当前代码证明。需要用诊断记录复现确认 |
| 琴弦时序可能拆裂 | 当前 D-pad 重排只处理 1–4 弦；5/6 弦的面键保留原时间 | 同拍内声部可能时间错开，是已知适配差异 |

因此代码方案先消除可确认的耦合和阻塞。25 ms/17 ms 等新时序是**试验起点**，需要目标游戏实际采样验证，不能只因 ViGEm 是虚拟设备就假定游戏一定能识别该脉冲。

## 2. 目标分层

```text
MIDI
  → 音乐计划（和键鼠一致：音符、弦、页、槽、原始起音）
  → 输出适配器
      ├─ 键鼠：扫描码/鼠标动作
      └─ 手柄：按目标游戏采样约束安排报告、压缩或丢弃低优先级内声部
  → GuitarScheduler：单调时钟、状态、截止策略、输入报告提交
```

`UseVirtualGamepad` 不再传入音乐算法，不得改变选弦/品格、和弦、模式选择或音符移调。它只用于选择输出适配器。手柄可因物理吞吐量不足而在**输出适配阶段**削减低优先级同时音，不得回头改写音乐计划。

建议引入独立类型，避免继续向算法传设备布尔值：

```csharp
public sealed record GuitarOutputProfile(
    GuitarOutputKind Kind,
    long StringHoldUs,
    long SameDpadReleaseUs,
    long DpadNeutralUs,
    long SlotLeadUs,
    long PageHoldUs,
    long PageReleaseGapUs);

public enum GuitarOutputKind { KeyboardMouse, VirtualGamepad }
```

`PlaybackService` 继续创建一份与设备无关的音乐计划；之后再调用类似：

```csharp
var planned = CompileGuitarMusic(rawNotes, playMode, musicOptions);
var outputProfile = _config.UseVirtualGamepad
    ? GuitarOutputProfiles.VirtualGamepad
    : GuitarOutputProfiles.KeyboardMouse;
var actions = GuitarOutputAdapter.Compile(planned, outputProfile, _config.WheelPreset);
```

## 3. 编译期解耦的逐文件改法

### `Guitar/FretConverter.cs`

- 从 `FretConverterOptions` 移除 `UseVirtualGamepad`，或保留为 obsolete 兼容字段但不得参与计算。
- `GetTransitionCost` 使用设备无关的 `WheelMouseSettleUs` 输入，不因 bool 选择不同 `rapidWindowUs` / `rapidPenalty`。
- 对音符路径只保留一致的页面/槽位、可达性、弦位移动目标。硬件是否能完整弹出密集和弦由后续输出适配处理。

把现有条件：

```csharp
long rapidWindowUs = opt.UseVirtualGamepad ? 180_000 : 320_000;
double rapidPenalty = opt.UseVirtualGamepad ? 3.0 : 6.0;
```

改为一个固定的**音乐位置模型**参数（取键鼠当前值作为迁移基准，之后只做一次有记录的全曲参数调优）：

```csharp
long rapidWindowUs = opt.RapidWindowUs;  // 对所有输出设备相同
double rapidPenalty = opt.RapidPenalty;  // 对所有输出设备相同
```

同理，将 `opt.UseVirtualGamepad || slotChanged` 这种输出设备分支改为单一音乐模型规则。设备特有的 slot lead 只能在生成输出动作时间表时使用。

### `Guitar/GuitarCompiler.cs`

- 移除 `UseVirtualGamepad` 对同弦音符二次推迟/过滤、重复音抑制和保持/释放节奏的影响。
- 同弦起音计划使用 MIDI/用户延音设置和共同的最短音乐时值，不把 Xbox D-pad 限制混进弦选择。
- 输出动作仍保留 `RequiredPage`、`RequiredSlot`、`NoteNumber`，供手柄适配器排序取舍。
- `GetWheelSettleUs` 移到输出适配器，或改为无设备参数的音乐编译器参数。

检查并移除该文件内所有 `options.UseVirtualGamepad` 分支，重点是 `CompileFretEvents`、重复攻击过滤、`KeepGamepadReleaseGap` 与 `GetWheelSettleUs`。

### `Guitar/HybridGuitarCompiler.cs`

- 从 `HybridCompilerOptions` 去掉 `UseVirtualGamepad`。
- `modeTransitionFloorUs`、槽位等待、弦最短保持、DP 候选成本采用统一的音乐计划参数。
- 移除该文件中 `UseVirtualGamepad ? ... : ...` 的规划分支。
- 编译完成后调用 `GuitarActionPlanner`（更名建议 `GamepadOutputPlanner`）做设备输出适配。

当前 `PlaybackService` 在 Mode 3 将手柄最小按住、释放和选槽参数直接写入 `HybridCompilerOptions`；需要把这些值拆成两组：`MusicPlanningOptions` 与 `GuitarOutputProfile`。不要把手柄输出 Profile 传入 Hybrid DP。

## 4. 建议的手柄基准时序

把 `GamepadInputTiming.cs` 变成唯一设备约束来源。先使用偏保守的采样值，不在多个编译器复制常量：

```csharp
namespace MidiAutoPlayer.Guitar;

internal static class GamepadInputTiming
{
    // 初始实验值；需用目标游戏验证。若漏采样，逐档增加，不要由编译器私自覆盖。
    public const long StringHoldUs = 25_000;
    public const long DpadNeutralUs = 17_000;
    public const long SameStringReleaseUs = 17_000;

    public const long SlotHoldUs = 50_000;
    public const long SlotSelectLeadUs = 32_000;

    public const long PageHoldUs = 50_000;
    public const long PageReleaseGapUs = 35_000;

    public const int StrumHoldMs = 50;
}
```

25 ms + 17 ms 理论上约 42 ms 一个方向脉冲；不是保证每秒 23.8 次稳定识别。若目标游戏在 60 Hz 输入采样，25 ms 约为 1.5 帧，但输入采样时相、轮询逻辑、前台帧率都可能降低识别率。

## 5. 重写 D-pad 排程：绝不将超载段原样下放

### 排程规则

1. 以 `RequiredPage + RequiredSlot + 原始攻击时间` 分组，不能跨组串弦。
2. PageNav、ModeSwitch、WheelSelect 是硬屏障。每根 D-pad 弦必须满足 `Up <= nextBarrierTime`；否则该音在适配阶段被标为 dropped，绝不拖到新页/新槽后发出。
3. 同起音的 5/6 弦面键保留原拍点。D-pad 组内先安排最高 `NoteNumber`（主旋律锚点），再安排其它内声部；只保留能在本组安全窗口内完成的音。
4. 对不同起音，不把后音挪到自己的下一次攻击之后；如吞吐量不够，削减低优先级音并记录原因。不要整体延迟后续旋律。
5. 输出动作必须成对：每个保留的 Down 都有一个明确 Up；被丢弃音的 Down/Up 一并移除。

### 伪代码（替换现有 `segmentFits` 放弃整段的行为）

```csharp
foreach (var attack in dpadAttacks.OrderBy(x => x.TimeUs))
{
    long nextAttackUs = FindNextAttackInSamePosition(attack);
    long nextBarrierUs = FindNextBarrier(attack);
    long endUs = Math.Min(nextAttackUs, nextBarrierUs);

    // 最高音先占原起音，保住旋律；其余音按剩余窗口逐个容纳。
    var voices = attack.Voices
        .OrderByDescending(v => v.NoteNumber)
        .ThenBy(v => v.StringNo)
        .ToArray();

    long cursorUs = attack.TimeUs;
    foreach (var voice in voices)
    {
        long downUs = voice.IsLead ? attack.TimeUs : cursorUs;
        long upUs = downUs + profile.StringHoldUs;
        if (upUs > endUs || !WithinAllowedLateness(voice, downUs))
        {
            DropPair(voice, "GamepadDpadCapacity");
            continue;
        }

        KeepPair(voice, downUs, upUs);
        cursorUs = upUs + profile.DpadNeutralUs;
    }
}
```

这是策略片段，不是可直接粘贴的完整类：当前 `GuitarAction` 没有 `IsLead`/`DroppedReason` 字段，也没有攻击帧聚合对象。实现时用 `NoteNumber` 找最高音锚点，并在诊断报告中增加 `GamepadDpadCapacity` 丢弃原因。若作品是块和弦且最高音不是用户定义旋律，后续可扩展显式 `VoiceRole`；第一版用最高音规则即可。

### 必须新增的边界检查

时间都用 `long` 微秒；不要通过负值哨兵和整数溢出计算边界。对无下一攻击/屏障的情况用 `long.MaxValue`，计算前做饱和减法：

```csharp
static long SaturatingSubtract(long value, long amount) =>
    value < long.MinValue + amount ? long.MinValue : value - amount;
```

## 6. 控制器改成无等待、显式报告

`VirtualGamepadController` 不应 `Sleep`、`Yield`、等待按住时间或拥有 Timer。改为每个 API 只更新一个报告并立即提交；Up/回中都由动作时间轴显式触发。

### API 形状

```csharp
public bool SetString(byte stringNo, bool isDown);
public bool SetSlot(int slot);         // 选槽方向报告
public bool NeutralizeSlot();          // 显式左摇杆回中
public bool SetPage(int direction, bool isDown);
public bool SetModeSwitch(bool isDown);
public bool SetStrum(MouseButton direction, bool isDown);
public void ResetAll();
```

`SetString` 只允许 1–4 弦通过 D-pad；如果另一 D-pad 方向仍处于 Down，返回 `false` 并记录 `ConflictingDpadState`，不可在内部等它释放。5/6 弦设置 Xbox A/X。`ResetAll` 不等待最低保持时长，立刻清除方向、面键、扳机、左右摇杆并提交报告，保证 stop/pause 尽快释放。

可按以下方式替换控制器里阻塞的琴弦发送骨架：

```csharp
public bool SetString(byte stringNo, bool isDown)
{
    if (stringNo is < 1 or > 6) return false;
    lock (_sync)
    {
        if (!EnsureConnected() || _controller is null) return false;

        bool anotherDpadHeld = false;
        if (stringNo <= 4 && isDown)
        {
            for (int i = 1; i <= 4; i++)
                if (i != stringNo && _heldStrings[i]) anotherDpadHeld = true;
        }
        if (anotherDpadHeld)
        {
            LastError = "ConflictingDpadState";
            return false;
        }

        var button = ResolveStringButton(stringNo);
        if (button is null) return false;
        _controller.SetButtonState(button.Value, isDown);
        _heldStrings[stringNo] = isDown;
        _controller.SubmitReport();
        return true;
    }
}
```

这段代码仅替换无等待的单次琴弦报告路径。所有 `WaitForHold`、`WaitForDpadNeutral`、`WaitSince`、`SendStrum` 内部 `Thread.Sleep`、`_slotNeutralTimer` 及其 generation 代码都应移除。

槽位回中时间应显式进入时间轴：

```csharp
// WheelSelect(t) → SetSlot(slot)
// WheelSelectNeutral(t + SlotHoldUs) → NeutralizeSlot()
// 第一个依赖该槽位的 StringDown 至少在 t + SlotSelectLeadUs
```

需要确认游戏把左摇杆方向当作“选槽脉冲”还是“持续选槽状态”。若游戏依赖持续状态，就不要定时回中；不要由 Timer 在调度器不知情时改变物理状态。

## 7. `GuitarAction` 与 `GuitarScheduler` 时间轴改造

### 新增显式 release action

当前有 `PageNavUp`、`ModeSwitchUp`，但没有选槽回中或扫弦结束事件。扩展 `GuitarActionType`：

```csharp
WheelSelectUp = 9, // 手柄 LS 回中；键鼠输出适配器忽略
StrumUp = 10       // 手柄右摇杆回中；键鼠 click 仍为短点击
```

每次 `WheelSelect` 编译时追加 `WheelSelectUp(TimeUs + SlotHoldUs)`。手柄扫弦由 `StrumClick` 生成 Down 和 `StrumUp(TimeUs + StrumHoldUs)`；键鼠编译仍可使用原鼠标点击事件。

### 调度器执行约束

- `GuitarScheduler` 仍按同一 `TimeUs` 排序、等待目标时刻；控制器调用不能睡眠。
- 同时间戳优先级固定为：琴弦/模式/翻页/扫弦的 Up → 控制 Down → 选槽 Down → 琴弦 Down。D-pad planner 必须已消除同一时间点多个 1–4 弦 Down。
- 每一个控制状态变化成功后更新 `GameStateMachine`；失败只对依赖该状态的动作记录 `InputFailed`，不要伪造页/槽状态。
- 硬屏障前有尚未 Up 的 D-pad 弦时，计划器应丢弃/重排内声部；scheduler 不要同步等待旧弦自然到期。
- `WheelSelect` 只发摇杆向量，不因 `CurrentSlot` 已是同值就丢失必要的重新选择报告。是否重发相同向量应由输出计划显式标记 `ForceReport`。
- 对已经迟到的音符：若其 `RequiredPage/Slot` 仍匹配且动作未超过明确的音符容忍窗，可立即发送并记 late；若跨越控制屏障或状态不匹配则跳过这一音并记原因。不要把“轻微迟到”改成整曲失败。
- 页面/模式切换报告失败后，状态保持旧值并进入恢复路径；后续音符不得仅凭编译期预期假设页面已改变。

当前调度器里仍有 `_gamepad.SetStringsBatch(...)`、`SetStringState(...)`、`SendStrum(...)` 的旧调用；需要统一改为上述逐事件 API。当前 `SendStrum` 内部 `Thread.Sleep` 是直接阻塞点；当前 `SetStringsBatch` 内部也会等待按住/中立时间。不要只删除 `StaggerDpad` 的串行延时而保留控制器阻塞。

## 8. 推荐落地顺序

1. **先做输入可观测性：** 诊断每个动作的计划/实际时间、动作类型、页槽、D-pad 状态、报告提交成功与否、丢弃原因。
2. **隔离纯音乐计划：** 相同曲目分别用键鼠/手柄编译并输出 `Page/Slot/String/NoteNumber` 对比；这些字段应一致。
3. **落地非阻塞控制器 API：** 移除内部定时器和等待，把琴弦 Up、槽位回中、扫弦回中放到动作列表。
4. **实现屏障安全的手柄适配器：** 过载时删掉低优先级内声部，不允许动作越过下一攻击/页槽控制屏障。
5. **加入可配置时序档位：** 25/17 ms 作为初始值；按目标游戏结果逐步调整到可稳定识别的最低值。
6. **最后调整调度恢复策略：** 只对明确的状态失步做重同步，不以一次迟到或一次漏音终止整场播放。

## 9. 验收条件

- 键鼠与手柄在**音乐计划层**每音映射的页/槽/弦/MIDI 音高一致；差异只存在于输出适配和其记录的丢弃音。
- 任何琴弦 Down/Up 成对；停止和暂停立即释放所有控制状态。
- 任一 D-pad Down 到 Up 满足 profile 最低保持；两个方向间包含必要中立时长。
- 没有琴弦动作落在不同页/槽的控制屏障之后仍携带旧 `RequiredPage/Slot`。
- 手柄报告 API 不包含 `Sleep`、忙等、Timer 或任务延迟；同一控制器状态只从 scheduler 线程提交。
- D-pad 容量不足时，诊断明确显示被丢弃的内声部；最高音和 5/6 弦不被低优先级音挤掉。
- 发生输入错误时有精确原因，清理路径释放手柄；普通迟到不会静默造成整曲失声。
